# Mellow Merchant Store Template Checklist

Use this checklist whenever you review a new storefront template. Mark each item as:

- `[A]` Available in the design
- `[M]` Missing but can be added
- `[H]` Available but should be hidden
- `[N/A]` Not needed for this merchant/store

The most important rule is: **a beautiful template is only suitable if its layout can accommodate Mellow’s actual store content and buying flows.**

15. Customer order details page
16. Customer settings page
17. Custom content page

The pages most likely to require hidden or custom sections are **checkout, account pages, payment pages, brand pages, reviews, and custom content pages**. These are usually missing from attractive frontend templates, but they are essential to the full Mellow store experience.

# Code-Verified Storefront Audit and Redesign Handoff

This section ties the general checklist above to the current Mellow implementation. It was assembled from `script/routes/web.php`, the storefront controllers, and the four Blade theme folders under `script/resources/views/frontend/`. It is a code inventory, not a browser QA report; routes and conditional states should still be exercised with representative store data before sign-off.

## Theme System and Scope

- Storefront views are selected by the store domain's `view_path` (`base_view()` in `script/app/Helper/helper.php`). The current theme folders are `arafa-cart`, `bazar`, `bigbag`, and `saka-cart`.
- Merchants select a theme from Seller → Online Store → Themes. `ThemeController@update` changes the domain's `template_id`; storefront view selection is resolved through the domain's `view_path`.
- All four themes provide the main layout, header, footer, homepage, shop, product detail, cart, checkout, thank-you, wishlist, custom page, account login/register/dashboard/orders/order detail/settings, and four payment handoff views (Paystack, Razorpay, Squad, Stripe).
- `arafa-cart`, `bazar`, and `saka-cart` also have shared menu/footer-menu partials. `bigbag` has a theme-specific edit-mode modal and a different header/cart presentation.
- Tracking-page templates exist only for `arafa-cart` and `bigbag`; the route exists for all stores. Treat the missing `bazar` and `saka-cart` view files as a verified coverage gap to resolve or explicitly account for in the new theme.

## Actual Storefront Route and Page Inventory

The same buyer route set is registered for both Mellow subdomains and merchant custom domains. Theme selection affects the view, not the route contract.

| Route or state | Current rendering | Redesign requirement |
|---|---|---|
| `/` | Theme homepage | Configured homepage sections and their empty/loading states |
| `/shop?src=…` | Theme shop view | Search term state; product listing and filters |
| `/category/{slug}/{id}` | Theme shop view with category context | Category title/context, category products and empty state; no dedicated category template today |
| `/brand/{slug}/{id}` | Theme shop view with brand context | Brand context/products; no dedicated brand template today |
| `/trending`, `/best-sales` | Theme shop view with collection context | Collection heading and listing; these are routes, not independent page templates |
| `/product/{slug}/{id}` | Theme product detail | Product media, dynamic options, stock/purchase states, reviews and related products |
| `/cart`, `/wishlist` | Theme cart/wishlist | Empty, populated, update/remove and feedback states |
| `/checkout` | Theme checkout | Guest/customer, delivery, payment, validation and processing states |
| `/thanks` | Theme thank-you page | Completed order confirmation; payment success redirects here |
| `/payment/payment-success` | Controller action then `/thanks` | No separate themed payment-success screen in the current flow |
| `/payment/payment-fail` | Controller flashes failure then redirects to `/checkout` | Checkout must render payment failure feedback and allow retry/change method |
| `/user/login`, `/user/register` | Theme account forms | Validation/error/success states; registration captures name, email, phone, password and confirmation |
| `/user/dashboard`, `/user/orders`, `/user/order/view/{id}`, `/user/settings` | Theme account views | Account navigation, order statuses/details, downloadable files, profile/password update feedback |

Customer password reset views are under `script/resources/views/auth/customer/passwords/`, outside the theme folders. `/user/password/reset` is registered outside the storefront route groups, so it is not tenant-theme-specific today. Include it in the redesign only if the reset experience is being brought into each store's visual shell.

## Cross-Theme Shared Store Content

Layouts read tenant/store data at render time. The new theme must tolerate optional or merchant-specific values rather than assuming demo content:

- Store logo/name, favicon, configured colors, currency symbol/position, enabled languages and locale/RTL direction.
- Merchant-created navigation/menu items, nested categories/menu entries, custom pages, social links, contact details and store policies where configured.
- Homepage slider images/links, promotional/banner ads, bump ads, featured categories/brands, category-with-products and brand-with-products, latest, random, offerable, trending and best-selling product sections. Several homepage collections load through `/get_home_page_products` and related JSON endpoints; handle sections independently when their data is empty or unavailable.
- Storefront routes also expose product search, shop attributes, featured attributes, category/brand lists, product lists, reviews and related products as JSON. These are data endpoints, not standalone pages.
- Product/card/detail data includes product name, media, category/brand, price and regular price, stock/SKU, affiliate URL, product options that can change price, attribute variations, review aggregates, and downloadable files on completed orders. Some fields are optional.

Do not assume the old checklist's generic wishlist items are current functionality. For example, quick view, dedicated brand/category pages, product image video, search suggestions/history, compare, newsletter, cookie consent, review images, FAQ/blog/app-download blocks, and shipping estimates were not found as buyer-facing implementations in the audited theme views/routes. Treat these as **new scope only if requested**, not as required parity. There is no evidence of a product quick-view modal in the current themes.

## Interaction-Only UI to Carry Into the Design

These states are easy to miss in a static page review and need design coverage even when the control is not initially open.

### Global shell and navigation

- Desktop/mobile navigation and nested menu/category dropdown behavior; menu data is merchant-configurable.
- Search form submits a query to `/shop`; the current route contract does not provide suggestion/autocomplete UI.
- Language dropdown/selector where languages are configured; selecting one changes the locale.
- Header wishlist/cart counters and cart preview/dropdown where the theme exposes it. Cart preview content includes item image/name, quantity, price, subtotal/total and checkout/cart actions.
- Theme color/store context and layout direction can vary by merchant and locale; verify contrast, long store names and navigation overflow.
- `bigbag` has an edit-mode/top banner and a “Customize Your Store” modal for merchant users. Its contents link to store setup areas (shipping, location, etc.); it is a merchant-only overlay, not ordinary buyer storefront content, and needs an explicit keep/remove decision for the new theme.

### Home and listing discovery

- Homepage category filter tabs and category/product carousels/sliders, with touch/mobile interaction where enabled.
- Shop sidebar filter groups expand/collapse. Existing filter coverage is narrower than the aspirational generic checklist; preserve the actual category/brand/price/attribute controls exposed by the current shop scripts and responses.
- Listing sort, pagination and result counts; category/brand/search context is passed into the same shop surface. Confirm available sort options and no-result states against `frontend/{theme}/js/shop.js` before implementation.
- Product cards expose product navigation, add-to-cart and add-to-wishlist behavior, sale/stock presentation, and in some themes hover/image interactions. Do not design a quick-view affordance unless the new feature is separately agreed.

### Product detail

- Main image and thumbnail gallery; lightbox/gallery behavior is included in `arafa-cart`, `bazar`, and `saka-cart` assets, while `bigbag` has its own scripts. Preserve zoom/lightbox, thumbnail selection and mobile swipe where provided.
- Attribute/variation selectors, optional product add-ons (checkbox or single-select groups), required-option validation, option-driven amount changes, quantity decrement/increment, and stock-limited quantity.
- In-stock, out-of-stock, affiliate-product and ordinary add-to-cart/purchase-now variants.
- Add-to-cart and wishlist are asynchronous in the detail scripts and update counters/feedback. Review tabs load review content and paginated results; the form has logged-in and login-required states, star selection, validation, submission success/error feedback.
- Previous/next product links and dynamically loaded related/latest products.

### Cart, checkout, and payment

- Cart item quantity is displayed, but the current cart pages do not expose quantity edit controls. Preserve item removal, clear-cart action, coupon entry with invalid/not-found feedback, empty-cart state, totals (subtotal/tax/shipping/discount/total), and cart preview updates/alerts. If quantity editing is wanted in the redesign, treat it as a behavior addition and confirm the server update contract first.
- Checkout has a returning-customer login panel (collapse in three themes; `bigbag` links to the login page), a link back to the cart to apply a coupon, customer/contact fields, optional account creation/password fields, notes, and inline validation/server errors.
- Delivery is tenant-dependent: some stores use hierarchical delivery locations and location-dependent shipping methods/prices; shipping can be optional/conditioned on the customer's shipping-payment setting. Pickup/order status is supported. Show or hide address/shipping inputs and fees based on the actual store configuration and selection.
- Checkout order summary includes item variant/option information, quantity, subtotal, discount, tax, delivery fee and total. Payment methods are merchant-enabled and can differ per store; do not hard-code a single global provider list.
- Place-order processing/disabled state, validation errors, gateway redirect/loading handoff, payment callback success, callback failure, retry/change-payment path and support feedback need explicit coverage. The current failure state returns to checkout; it is not an independent failure-page template.
- Stripe can render card entry/errors; Paystack/Razorpay/Squad have provider-specific browser handoff and callback forms. Other available providers can complete via external redirects/callbacks. Keep integration mechanics intact while changing presentation.

### Account and order states

- Login validation and failed login feedback, remember-me checkbox, forgot-password link, registration validation (including duplicate email/phone), and account-created/login state.
- Dashboard links to orders/settings; orders list has paginated data and multiple order/payment statuses (including ready-for-pickup); order details include shipping address, payment method/status, item options, amounts and sometimes downloadable files.
- Profile name/email/password update; password change uses current password, new password and confirmation, with success/error feedback.
- Order tracking by transaction ID has guest and logged-in paths. Digital/downloadable order files are only available in eligible order states; allow for download links in account order detail.

## Verified Scope Gaps and Design Decisions to Set Before Handoff

- Confirm whether to add missing `bazar`/`saka-cart` tracking views or remove/redirect the route for those themes.
- Decide whether the new theme should preserve `bigbag` merchant edit-mode modal/banner; its current presence is unique and separate from buyer-facing store design.
- Decide whether the non-theme password reset pages should be visually integrated into the selected tenant theme.
- Treat quick view, dedicated brand/category layouts, payment failure page, search autocomplete, newsletter, consent, ratings/review images, rich FAQ/blog sections, comparison and checkout express wallets as not present in the audited theme route/view contract unless verified elsewhere or explicitly added to scope.
- Set empty/loading/error designs for dynamic home sections, listings, product media/reviews, cart, checkout and customer account. Existing Blade conditionals and async endpoints make these real states even if screenshots rarely show them.
- Verify at minimum: desktop and small mobile; long/missing logo and store name; no homepage banners/categories/products; empty/one/many cart items; product with multiple required options and out of stock; guest vs returning customer checkout; delivery vs pickup and shipping fee on/off; each enabled payment method success/failure; logged-out vs logged-in review; empty/populated orders; RTL locale.
